# S2 · 搜集（先选数据源，再谈检索）

> **这一节的第一句话，是这次全量实测换来的：**
> **公开新闻索引适合做「专题样本」，做不了「月度全域台账」。**
>
> 实测数据（2026-08）：维基「当前事件」31 天全抓、99 条候选、结构化抽取 + 战争语境分流后，
> 按口径只能计入 **8 条**。而尼日利亚一国官方口径同月就有 **500 起安全事件**。
> 差的不是检索技巧，是**数据源的收录密度**。

## 零、先做这个判断（不然后面全是白费）

开工前必须回答一句：**这份台账要求「量级完整」还是「专题样本」？**

| 要求 | 该用什么数据源 | 预期条数 | 工时 |
|---|---|---|---|
| **月度全域台账**（要求尽量不遗漏） | **ACLED / UCDP**（结构化冲突数据库）+ 新闻补漏 | 数十至数百 | 数天 |
| **专题样本**（某组织、某国、某类型） | 公开新闻索引 + 逐源点名 | 十几至几十 | 数小时 |
| **快速摸底**（先看看有没有料） | 维基「当前事件」日历 | 十几 | 1–2 小时 |

**选错源的代价**：用维基去做月度台账，无论脚本写得多好，结果都只有个位数到十几条。
这不是失败，是**选错了工具**。

## 一、结构化冲突数据库（月度台账的首选）

| 源 | 覆盖 | 费用 | 关键字段 | 怎么用 |
|---|---|---|---|---|
| **ACLED** | 全球，事件级，含经纬度、行为体、死亡数 | 学术邮箱可申请免费额度；商业付费 | `event_date, event_type, sub_event_type, actor1, actor2, fatalities, latitude, longitude, source` | 最对口。`event_type` 筛 `Battles / Explosions/Remote violence / Violence against civilians` |
| **UCDP**（乌普萨拉） | 全球，组织-国家冲突事件级 | **完全免费**，月度/年度发布 | `date_start, side_a, side_b, deaths_civilians, deaths_a, deaths_b, source_article` | 免费首选。GED 数据集可按国家/年月下载 CSV |
| **GDELT** | 全球新闻事件，实时 | 免费 | CAMEO 事件编码，粒度粗 | 只适合找线索，不适合直接计数 |

**关键提醒**：这些库的「事件」定义与你委托方的口径**不一定一致**。
拿到数据后仍必须逐条按判定链重判 —— 但它们的**召回率**远高于新闻检索，
能把「漏检」这个最大风险压下去。

## 二、公开新闻索引（补漏与专题，不是主力）

### 主路径：用你手上任何可用的检索能力

不同机器上有什么就用什么，本节不假设你有某个特定工具：

1. **`web_search`（宿主工具）** —— 几乎所有 agent 都有
2. **直接抓 URL**（requests / curl）—— 拿到候选链接后取正文与日期
3. **站内点名**（`site:域名 关键词`）—— 效果常好于宽泛检索
4. 可选增强：Tavily / TinyFish / CNKI —— 没有就跳过

**「必须逐档试过 6 档才能说检索失败」这条不成立** —— 那是给装了全部通道的机器写的。
正确判据：**至少两路独立索引交叉，且每一路失败的都记了原因**。

### 维基「当前事件」日历（快速摸底与补漏）

免费、无需密钥、每天更新、每条标原出处，是**把量级基线拉到正确水平的最低成本手段**：

```bash
python scripts/harvest_wiki_events.py --month 2026-08 \
  --fetch-cmd "你的抓取命令 {url}" --out 候选.jsonl
```

它自带三条约束（都来自实测踩坑）：
- **数量下限**：少于 `--min-items`（默认 80）直接 exit 2
- **区分三种失败**：抓取失败 / 解析失败 / 当日空页（不许混成一个「无事件」）
- **内容校验**：某些页对 raw 接口返回网页导航壳（含 "Jump to content"），
  长度上千、状态码 200，看着像抓成功了其实一个字没有

**但要知道它的天花板**：维基编辑者偏欧美，非洲小规模袭击几乎不进。
用它做月度台账，结果会系统性偏向「大国战争」而漏掉「非洲日常袭击」。

## 三、检索矩阵（用在补漏阶段）

| 类 | 做法 | 何时用 |
|---|---|---|
| **① 逐源点名** | 每个信源单独一次站内检索（`site:` 或 `allowed_domains`） | **性价比最高**，补漏首选 |
| **② 带引号日期串按日枚举** | 多套模板 × 每天 | 第二有效 |
| ③ 国家 × 组织 × 类型 | 常见组合 | 初筛 |
| ④ 国家 × 本地语言 | 法语 / 阿拉伯语 / 斯瓦希里语 | **补非洲缺口的关键** |
| ⑤ 国家 × 周段 | 按周切 | 辅助 |

**两招最有效的都靠「具体化」**：点名到域名、点名到日期、点名到本地语种。
宽泛英文关键词检索召回最差 —— 这是本次实测最明确的教训。

## 四、单域名点名，不要多域名合并

实测差异极大：
- 多域名合并检索：某事件只回了旧年文章
- 改成 `site:目标域名` 单域名点名：立刻命中 2 篇当月专文

**想覆盖 N 家源，就发 N 次查询。**

## 五、检索通道坏了要往下走，不许终止

```
web_search 失败（402/欠费/限流/空结果）
  → 换直连抓取（requests/curl）
  → 换站内点名
  → 换可选增强通道（Tavily/TinyFish/CNKI）
  → 全都不行才说「检索不可用」，且必须列出每档失败原因
```

**铁律**：默认检索失败 ≠ 检索不可用。**同一问题至少两路独立索引交叉。**

## 六、先做环境核验，再宣布能力不可用

任何「某能力不可用」的结论之前：

1. **先读配置层**（provider / 后端 / 密钥），不要只看工具名
2. 发一次**真实探针**（配置在岗 ≠ 额度可用）
3. 判据：说不可用时要能列出「核验过的路径 + 看到的返回值」

## 七、代理与网络（本次实测踩到的坑）

- **最常见的坑：代理环境变量指向一个没启动的代理。** 此时所有请求（含国内站）全部失败，
  看起来像「断网」，其实是 `HTTP_PROXY/HTTPS_PROXY` 指了个空端口。
  诊断：`unset HTTP_PROXY HTTPS_PROXY http_proxy https_proxy` 后重试；若立刻通，就是这个问题。
  Python requests 用 `session.trust_env = False`。
- **国内网络常连不上 en.wikipedia.org**：必须用 `--fetch-cmd` 指定一个能取网页的命令，
  否则 31 天全失败。
- 批量抓取要限速（并发 1–4），否则容易触发限流。
